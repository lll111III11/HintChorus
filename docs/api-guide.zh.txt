0. 先看前提: 本底层有两种运行状态
────────────────────────────────────────────────────────────────────────────────

  行为完全取决于配置, 先确认你在哪一档:

  状态甲  intercept_third_party_ui: false   (默认, 最保守)
          只有 SSS 强力复写在兜底。提示条与广播【完全不接管】,
          原版写法行为 100% 不变。

  状态乙  intercept_third_party_ui: true
          额外接管 提示条(Hint) + 屏幕广播(Broadcast),
          按"调用方插件"自动分配独立 UiId 信口。

  第二部分里凡是标了 【需状态乙】的条目, 只在拦截层开启时才成立。

  引入命名空间:
      using HintChorus;                     // 门面 UiIsolation
      using HintChorus.Core.Interfaces;     // 契约接口
      using HintChorus.Core.Enums;          // 枚举
      using HintChorus.Core.Models;         // UiScope / RegisterResult
      using HintChorus.Core.Identity;       // UiId 目录


  ────────────────────────────────────────────────────────────────────────────
  0.1 它是怎么把"一个口"变成"很多信口"的(务必先理解这一段)
  ────────────────────────────────────────────────────────────────────────────

  先说清一个前提: 屏幕提示在服务器端【没有状态】。

  服务器端唯一的下发入口是 HintDisplay 上的 Show(Hint)。它做的事情只有两件:
  查一下该玩家连接此刻是否被抑制, 然后把这条提示作为一条网络消息发给他的客户端。
  它既不保存"当前显示的是什么", 也不排队。

  关键结论:
    · 服务器端【没有】"当前提示"变量, 也【没有】队列 —— 每次 Show 就是发一条消息。
    · 真正"只有一个槽"的是【客户端】: 收到一条就替换掉当前显示的那条。
    · 所以"扩大口"在服务器端唯一的着力点就是 —— 【谁把这条消息发出去】。

  本底层的做法(四步):

    ① 拦截   所有 Show(Hint) 调用(插件 + 游戏原生)都被拦下, 不直接放行。
    ② 路由   沿调用栈解析出"这是谁、哪个方法、哪个偏移" → 派生 UiId
             → 写入该 UiId 专属信口(信口内容 = 一串带到期时间的条目)。
             本底层自己的合并结果带自研标记, 直接放行(防自环)。
    ③ 合成   本核心成为【唯一写者】: 把全部存活信口的条目按优先级拼成一条
             复合 TextHint(多行), 由它一个人发给客户端。
    ④ 驱动   每次路由写入都【立刻】触发一次重算(40ms 快速通道),
             而不是等 750ms 的整轮刷新 —— 所以调用方那一次 Show 被吞掉后,
             内容几乎瞬时又以"合并结果里属于它的那一行"出现。

  由此得到三个性质:
    · 隔离: 每个 UiId 独立信口, 重叠写同一个 API 也不会串到一起, 各自分配 UiId。
    · 不抢占: 屏幕内容恒等于"全部存活信口的合并", 没有谁把谁顶掉的窗口期。
    · 各自到期: 每条条目有自己的到期时间, A 的 3 秒和 B 的 10 秒各走各的。

  参数与副作用:
    NativeHintPolicy   原生提示是否也纳入路由。默认 Isolate(纳入, 否则它会直发客户端
                       顶掉合并结果, 与下一轮刷新来回覆盖 = 闪烁)。
    HintRefreshInterval 整轮刷新间隔(默认 0.75s), 负责条目自然过期与续期下发。
    快速通道 40ms 为内置常量, 空闲时目标集合为空, 不产生额外开销。

1. 常驻状态栏(内容固定)
────────────────────────────────────────────────────────────────────────────────

  IHintChannel ch = UiIsolation.RegisterHintChannel(
      "MyPlugin.Hud",                      // moduleId: 全局唯一, 被占用则返回 null(绝不抢占)
      "HUD",                               // displayName: 行首 [标签]
      "初始内容",                          // 初始文本
      duration: 3f,                        // 持续时长(秒)
      priority: (byte)HintChannelPriority.High);   // 越小越靠上

  ch.SetText("血量 75");                   // 更新内容, 下次刷新自动重发
  ch.Enabled      = false;                 // 单独停用本通道(不影响别人)
  ch.ShowLabel    = true;                  // 是否显示 [HUD]
  ch.Alignment    = HintAlignment.Right;   // Left / Center / Right
  ch.Duration     = 5f;
  ch.Priority     = 100;
  ch.ReceiverFilter = hub => !hub.isLocalPlayer;   // 按游戏原生 ReferenceHub 过滤

  UiIsolation.GetHintChannel("MyPlugin.Hud");       // 查询
  UiIsolation.UnregisterHintChannel("MyPlugin.Hud"); // 注销(只删自己的)
  UiIsolation.HintChannels;                          // 全部通道 ID

  要点: moduleId 是你自己起的名, 全局唯一。多个插件各自注册各自的, 互不覆盖。

2. 每玩家不同的动态内容(推荐做法)
────────────────────────────────────────────────────────────────────────────────

  底层每个刷新周期会对每个玩家调用一次 TryGetText, 你【不要】再自己起计时器刷 UI。

  public sealed class MyHud : IHintTextSource
  {
      public string ModuleId    => "MyPlugin.Hud";
      public string DisplayName => "状态";
      public byte   Priority    => (byte)HintChannelPriority.Low;

      public bool TryGetText(ReferenceHub hub, out string text)
      {
          text = $"HP {hub.playerStats.GetModule<HealthStat>().CurValue:F0}";
          return true;      // 返回 false = 该玩家这一行不显示
      }
  }

  UiIsolation.RegisterHintSource(new MyHud());
  UiIsolation.UnregisterHintSource("MyPlugin.Hud");
  UiIsolation.HintSources;

  要点: 底层完全不感知你的玩法逻辑, 只负责合并渲染。

2.2 (c) 完全不用改 —— 原样调用, 行为一字不变
────────────────────────────────────────────────────────────────────────────────

  这些根本不经过被接管的通道, 也不需要你动任何代码:

  · 控制台消息      player.SendConsoleMessage(msg, color)
  · 世界空间文字     TextToy.Create(...) / PrimitiveObjectToy / LightSourceToy
                    (整个 AdminToy 家族, 是世界物体不是屏幕 UI)
  · CASSIE 语音     Cassie.Message(...) / Announcer
  · 命中标记        player.SendHitMarker(size)
  · SSS 分页重载    ServerSpecificSettingsSync.SendToPlayer(hub, collection, version)
                    (这个重载由官方分页示例使用, 底层【刻意不拦】,
                     因为强改会破坏"显式指定集合"的分页语义)
  · 所有非 UI API   player.Heal / SetRole / Damage / AddItem / SetAmmo ...
                    Round.* / Server.* / Map.* / Warhead.* / Cassie.*
  · 所有事件订阅    PlayerEvents.* / ServerEvents.*
                    (LabAPI 自带逐订阅者异常隔离, 不需要额外包裹)
  · 插件骨架        Plugin<TConfig> / LoadConfigs / Config / SaveConfig / Priority
  · SSS 原始写法    ServerSpecificSettingsSync.DefinedSettings = 我的数组; SendToAll();
                    你的设置项照常生效。区别只是: 底层会在下发前把"本核心注册的"
                    设置项拼回数组 —— 也就是说, 这个经典写法【不会再清掉别人的 UI】了。
                    这是官方文档警告过的坑, 现在被自动兜住, 对你是纯收益。


────────────────────────────────────────────────────────────────────────────────
2.3 (d) 不用改写法 —— 原样调用, 调度由底层接管【需状态乙】
────────────────────────────────────────────────────────────────────────────────

  这一类是"白拿的收益": 插件作者完全不需要知道本底层存在。

  · player.SendHint(文本, 时长)
    → 自动归因到该插件自己的 UiId 信口。文字照常显示, 并且不再被别的插件顶掉。
      语义变化: 进入合并管线 —— 按优先级排序、同文本去重续期、
      受 MaxEntries / MaxDuration 上限约束。

  · hub.hints.Show(new TextHint(...))
    → 同上。原生写法与 LabAPI 封装走的是同一个 HintDisplay.Show, 归因路径一致。

  · player.SendBroadcast(文本, 时长) / Server.SendBroadcast(文本, 时长)
    → 首次出现【零延迟放行】; 存活期内重复的相同文本被去重抑制
      (防止插件"每秒重发"把同一条广播叠成 N 条)。

  · ServerSpecificSettingsSync.DefinedSettings = 我的数组; SendToAll();
    → 同 (c), 两个状态下都安全。

  副作用说明: 合并后玩家看到的是"一条复合提示", 由底层统一排版。
              如果你依赖原版"后发覆盖先发"的观感, 请关掉 intercept_third_party_ui。

2.5 (a) 已经完全失效 —— 必须改写法或改配置
────────────────────────────────────────────────────────────────────────────────

  (a-1) player.ClearBroadcasts()  /  Server.ClearBroadcasts()
        状态: 状态乙下【被吞掉】, 广播清不掉。
        原因: 它内部走 Broadcast.TargetClearElements, 正是底层打的补丁。
              判定调用方是插件时直接抑制。
        目的: 防止一个插件把【别人的】广播一起清掉。
        不受影响: 管理端命令 / 游戏自身 / 服务器控制台。
        恢复原行为: 配置 BlockThirdPartyBroadcastClear: false
        替代写法:   如果你只想控制自己的内容, 用第 1/2 节的通道或第 3 节的
                    ShowTransient —— 它们天然只影响自己那一份。

  (a-2) player.SendBroadcast(文本, 时长, flags, shouldClearPrevious: true)
        状态: 状态乙下"清除部分"失效, 等价于 shouldClearPrevious: false。
        原因: 已核实 LabApi 源码(Server.cs L473) ——
              shouldClearPrevious 为真时先调 ClearBroadcasts(player),
              再调 Broadcast.TargetAddElement。前半段被补丁吞掉。
        实际表现: 广播【照常发出】, 只是不再清掉别人已有的广播。
        恢复原行为: 同 (a-1), 配置 BlockThirdPartyBroadcastClear: false

  (a-3) 自己 Harmony patch 了 HintDisplay.Show 的第三方 UI 框架
        (典型: HintServiceMeow 这类"接管提示显示"的框架)
        状态: 状态乙下【整个框架失效】。
        原因: 底层的补丁前缀带 [HarmonyPriority(Priority.First)] (800, 最高档),
              且对插件发出的提示【返回 false 吞掉调用】。
              Harmony 的规则是 prefix 返回 false 就短路 —— 对方的前缀根本不会执行。
        这是最需要提前知道的一条:
              【两套接管 HintDisplay.Show 的方案不能同时开。】
        处理办法(二选一):
              1) 卸载/停用该框架, 用本底层统一接管;
              2) 把 intercept_third_party_ui 设为 false ——
                 此时本底层只做 SSS 兜底, 完全不碰提示条, 双方共存。

  (a-4) 注意: 下面这条【没有】失效, 不要误判
        ServerSpecificSettingsSync.SendToPlayer(hub, collection, versionOverride)
        这个重载底层刻意不拦, 分页语义完整保留。见 (c)。


────────────────────────────────────────────────────────────────────────────────
2.6 特例: 带 {0} 占位符的提示【必读】
────────────────────────────────────────────────────────────────────────────────

  这类写法(客户端插值的动态数值)会被底层【放行原生】, 不参与隔离:

      player.SendHint("剩余 {0} 发",
          new HintParameter[] { new IntHintParameter(ammo) }, null, 3f);

      hub.hints.Show(new TextHint("剩余 {0} 发",
          new HintParameter[] { new IntHintParameter(ammo) }, null, 5f));

  原因:
      {0} 是客户端用 HintParameter 实时插值的。底层的合并渲染只搬运纯文本,
      无法保真插值 —— 如果硬接管, {0} 会渲染成空串。
      数据丢失比"不隔离"更糟, 所以底层检测到文本含 { 就原样放行。

  影响:
      这类提示的写法与行为【完全不变】(归入 (d)),
      代价是【不参与 UiId 隔离】, 仍可能被其它插件的提示顶掉。

  想让它也隔离:
      自己在插件里先插值成纯文本再发 ——

      UiIsolation.ShowTransient(hub, $"剩余 {ammo} 发", 3f);   // 已是纯文本 -> 走隔离管线


────────────────────────────────────────────────────────────────────────────────
2.7 社区插件专题
────────────────────────────────────────────────────────────────────────────────

  本服的 plugin 目录里既有 LabAPI 插件, 也有 Exiled 桥接的插件。

  (1) LabAPI 插件  (AutoTFF-LabApi、CustomDoor、MapLightBooster、NamePrefix ...)
      走 LabAPI 包装类 -> 最终落到同一个 HintDisplay.Show / Broadcast.*
      → 归入 (d): 写法不用改, 状态乙下自动获得独立信口。

  (2) Exiled 插件  (通过 Exiled.Loader.dll 桥接运行)
      Exiled 的 Player.ShowHint / Player.Broadcast / Player.CurrentHint
      内部同样调用 HintDisplay.Show, 命中同一个拦截点。
      → 归入 (d): 写法不用改。
      → 例外: Exiled 的 CurrentHint 是"自己维护一份提示"的写法,
              与我们的合并管线并存时, 它那一份仍由它自己显示。

  (3) 自带显示框架的插件  (HintServiceMeow 类)
      → 归入 (a-3): 状态乙下会被压制。必须先决定用哪一套。

  (4) 只用世界物体做 UI 的插件  (TextToy / 光源 / 载具类)
      → 归入 (c): 完全不受影响。

  (5) 只做玩法逻辑的插件  (EXPAS、TrainBot、BGMCC 等)
      → 归入 (c): 没碰屏幕 UI 通道, 完全不受影响。


────────────────────────────────────────────────────────────────────────────────
2.8 快速决策: 我该不该开拦截层?
────────────────────────────────────────────────────────────────────────────────

  情形一: 你只是被"设置页 UI 全部消失"坑过, 提示条其实还行
          配置:  intercept_third_party_ui: false
                  EnableSssRegistry: true
                  EnableSssForceRewrite: true
          结果:  提示/广播行为 100% 不变; 设置页有 SSS 兜底, 不会再被清空。
                  这是推荐的第一步。

  情形二: 你确实被"多个插件提示互相顶掉"烦到
          配置:  intercept_third_party_ui: true
                  InterceptHints: true
                  InterceptBroadcasts: true
                  AutoAttributeThirdPartyUi: true
                  UiIdGranularity: Method
          前置:  先把服务器上【自己也 patch HintDisplay.Show】的框架停用, 否则它们失效。
          结果:  所有插件的提示各占一个信口, 不再互相覆盖。

  情形三: 有插件依赖 ClearBroadcasts() 清屏
          配置:  BlockThirdPartyBroadcastClear: false
          结果:  (a-1)(a-2) 的行为恢复, 代价是放弃"禁止插件清别人广播"的隔离。

  情形四: 原生提示的观感必须保持原版(不允许和插件 HUD 拼在一起)
          配置:  NativeHintPolicy: PassThrough
          代价:  原生提示会直发客户端顶掉合并结果, 与下一轮刷新来回覆盖
                 —— 表现为闪烁。这是唯一需要这一档的场合。
          注:    默认是 Isolate —— 原生提示同样并进合并结果, 玩家能同时看到,
                 排版服从底层规则, 但【不再互相顶】。

2.9 排障: 我的提示去哪了?
────────────────────────────────────────────────────────────────────────────────

  代码侧:
      UiIsolation.AttributedPlugins;                       // 被归因到的插件清单
      UiIsolation.UiIds.Records;                           // 信口 <-> 插件/方法/命中次数
      UiIsolation.GetSlots(UiSurface.Hint, "你的插件名");    // 你占的信口
      UiIsolation.CreateDiagnosticsReport();               // 完整报告

  日志关键词:
      已在其它插件之前安装 UI 拦截补丁(顺序 #N)   -> 引导器抢位成功
      已安装 SSS 强力复写补丁                     -> SSS 最后一道防线就位
      检测到有插件整体覆盖了 ... DefinedSettings   -> 防劫持守卫已自动合并恢复
      注册口 'xxx' 已存在                         -> moduleId 被占用
      SettingId 冲突, 已拒绝注册                  -> SSS 端口撞车, 改自己的 ID 段
      抛异常(已放行原生) / 已隔离                 -> 拦截层自身或插件回调异常, 已安全降级

  归因显示成"公共库名"而不是你的插件名:
      说明你的插件是通过某个共享库发的提示 —— 属正常现象, 隔离依然生效。

2.10 一句话总结
────────────────────────────────────────────────────────────────────────────────

  绝大多数原版写法【照常能用】。
  真正需要你动手的只有三类:
      1) 想做出原版做不到的 UI(常驻多块 / 每玩家不同 / 精确顺序) -> 用第一部分 1-3 节;
      2) 设置页控件                                -> 用第一部分第 4 节;
      3) 广播的"清除"类操作 + 自带 Show 补丁的框架  -> 见 2.5, 改配置或换写法。

================================================================================
【屏幕位置】三类写法(2026-10-07 新增)
================================================================================

游戏只给一条提示口, 所以"位置"最终都要折算成行级 <voffset>。本插件把三类来源
统一到一套九宫格锚点上, 解析优先级为:
    显式 API -> 文本标记 -> 自带位置标签 -> 名称目录 -> 默认(底部自然堆叠)

锚点取值(英文或中文皆可):
    top-left | top | top-right
    middle-left | middle | middle-right
    bottom-left | bottom | bottom-right
    也接受缩写 tl / tr / mc 与 左上 / 中部 / 右下 等。

--------------------------------------------------------------------------------
1) 兼容原有写法 —— 插件什么都不用做
--------------------------------------------------------------------------------
若插件文本里已经自带位置标签(<voffset> / <pos> / <align> / <line-height> /
<margin> / <indent>), 本插件判定为"插件自己摆了位", 原样放行、绝不重排。
开关: honor_plugin_position_syntax (默认 true)

--------------------------------------------------------------------------------
2) 自有写法 · 文本标记(零依赖, 不引用本插件也能用)
--------------------------------------------------------------------------------
在提示文本里写 {{hc:...}}, 本插件解析后会把标记从文本里剥掉(玩家看不到):

    "{{hc:top-right}} 本回合得分: 12"
    "{{hc:pos=middle,offset=-90}} Lv.5  经验 320/500"

    offset 以 voffset 为单位, 正数向上(参考: 整屏约 2140); 
    "屏幕中间再往下 90" 即 offset=-90。
开关: enable_position_markers (默认 true)

--------------------------------------------------------------------------------
3) 自有写法 · C# API(引用本插件的作者)
--------------------------------------------------------------------------------
    using HintChorus.Core.Layout;

    // 在插件加载阶段声明一次即可(信口尚未创建也生效)
    UiIsolation.SetHintPosition("MyPlugin", HintAnchor.MiddleCenter, -90f);
    UiIsolation.ClearHintPosition("MyPlugin");   // 撤销, 回到自动推断

--------------------------------------------------------------------------------
4) 自动排版(保底)
--------------------------------------------------------------------------------
未声明位置、也没有自带位置标签的插件, 按名称查"已收录表 + 功能区关键词"推断:
    exp / level / rank / 经验 / 等级   -> 中部居中, 下移 90
    score / board / 排行 / 战绩        -> 右上
    kill / feed / 击杀 / 淘汰          -> 左上
    timer / countdown / 倒计时         -> 顶部居中
    team / roster / 队伍 / 玩家列表     -> 中右
    music / bgm / 点歌                 -> 右下
    chat / 聊天                        -> 左下
    hud / status / 状态 / 面板          -> 左下
开关: auto_layout_by_plugin_name (默认 true)

服主可在配置里覆盖任何插件的落点(无需改插件):
    position_overrides:
      MyPlugin: top-right
      LevelSystem: middle,offset=-90

--------------------------------------------------------------------------------
保底不变: 所有插件都在默认位置时, 合成输出与旧版逐字一致; 定位只在真的用到时介入。
